# Benchmarking PostgreSQL on EKS: WEKA vs. Standard Block Storage

A reproducible AWS demo for the blog post *"Hands-On: Benchmarking PostgreSQL
on Kubernetes with WEKA vs. Standard Block Storage."* Terraform stands up an EKS
cluster with a dedicated WEKA storage backend, deploys PostgreSQL 16 **twice**
— once on gp3 EBS ("standard block"), once on WEKA via CSI — and runs `pgbench`
at increasing client concurrency to make the storage-saturation pattern visible.

> [!WARNING]
> **This costs real money** (~$15–25/hr with the cost-optimized defaults: 6×
> i3en.2xlarge WEKA backend + EKS nodes + NAT + ALB). It also requires WEKA
> credentials. **Run `make destroy` as soon as you're done.**

## Architecture

```
                          VPC (10.0.0.0/16)
   AZ-a (private)                                AZ-b (private)
   ┌───────────────────────────────┐            ┌──────────────────┐
   │ WEKA backend: 6× i3en.2xlarge  │            │ WEKA ALB (2nd AZ)│
   │ (placement group, NVMe)        │            │ EKS control plane│
   │                                │            └──────────────────┘
   │ EKS client nodes (c6i.4xlarge) │
   │  ├─ WEKA client containers     │  ── CSI ──► WEKA filesystem
   │  ├─ postgres-weka  (WEKA PVC)  │
   │  ├─ postgres-standard (gp3 PVC)│  ── EBS ──► gp3 volume
   │  └─ pgbench-runner             │
   └───────────────────────────────┘
   EKS system nodes (m6i.large): operator controller, EBS CSI controller, CoreDNS
```

Both PostgreSQL instances run on **identical c6i.4xlarge client nodes**, so the
only variable between them is the storage layer.

```

  run-benchmark.sh       pgbench 4/16/32/64 → results table

  weka/              WEKA operator/CSI/StorageClass manifests (vendored)

```

## Prerequisites

- AWS account + credentials (`aws configure`) with permissions for VPC, EKS, EC2,
  IAM, Secrets Manager, Lambda, Step Functions.
- Terraform >= 1.5, `kubectl`, `helm` 3.x, `jq`, `aws` CLI.
- A **get.weka.io token** and **Quay.io credentials** (both from
  [get.weka.io](https://get.weka.io)) — required to download WEKA and pull its
  container images.

## Configure

Set the three layers to the same `cluster_name` and `region`.

```bash
cp terraform/10-weka-backend/terraform.tfvars.example terraform/10-weka-backend/terraform.tfvars
cp terraform/20-eks/terraform.tfvars.example          terraform/20-eks/terraform.tfvars
# (00-vpc uses defaults; override region/cluster_name there if you change them)
```

Edit `terraform/10-weka-backend/terraform.tfvars` and fill in
`get_weka_io_token`. Everything else is handled for you: subnets are wired
between layers via Terraform remote state, and the EC2 key pair is
auto-generated by the `00-vpc` layer (private key saved to
`terraform/00-vpc/<cluster_name>-key.pem`, git-ignored) — you never copy a
subnet ID or supply a key pair by hand.

## Deploy

```bash
export QUAY_USERNAME=...   # from get.weka.io
export QUAY_PASSWORD=...

make infra      # vpc → backend → eks  (~25–35 min total)
make apps       # WEKA operator/CSI/client + both PostgreSQL instances
make bench      # run pgbench, write results/results-<timestamp>.md
```

Or step by step: `make vpc`, `make backend`, `make eks`, `make weka`,
`make postgres`, `make bench`. Run `make help` for all targets.

### Wait for the WEKA backend to clusterize

The backend forms its cluster at boot (~10–15 min). Watch it:

```bash
aws lambda invoke --function-name weka-$(cd terraform/10-weka-backend && terraform output -raw cluster_name)-status-lambda \
  --payload '{"type":"progress"}' --region us-west-2 \
  --cli-binary-format raw-in-base64-out /dev/stdout 2>/dev/null | jq '.summary'
```

`summary.clusterized` must be `true` before `make weka`. You can run `make eks`
in parallel while it forms.

## Verify

```bash
kubectl get nodes                                            # all Ready
kubectl get nodes -l weka.io/supports-clients=true           # client nodes
kubectl get wekaclient -n weka-operator-system               # Running
kubectl get sc                                               # standard-block + storageclass-wekafs-dir-api
kubectl get pods -n benchmark -o wide                        # both DBs on different client nodes
kubectl get pvc  -n benchmark                                # both Bound
```

## Run the benchmark

```bash
make bench
# or with custom parameters:
./scripts/run-benchmark.sh --scale 100 --duration 60 --clients "4 16 32 64"
```

This initializes a scale-1000 (~15 GB) pgbench dataset on both instances, then
runs each concurrency level against both and writes a Markdown table to
`results/`. The dataset deliberately exceeds `shared_buffers` (4 GB) and the pod
memory limit, so reads hit storage and the comparison is **storage-bound**.

> [!NOTE]
> Scale factor matters. At scale 100 (~1.5 GB) the dataset fits entirely in
> `shared_buffers`, so the workload is CPU/WAL-bound, not storage-bound — WEKA
> still wins on latency at low concurrency, but gp3 catches up as CPU saturates.
> Use a scale factor that exceeds RAM (default 1000) to see the storage layer
> become the bottleneck.

## Teardown

```bash
make destroy    # removes apps, then EKS, backend, and VPC
```

If a layer fails to destroy, run `terraform -chdir=terraform/<layer> destroy`
directly. The WEKA backend defines a `pre_terraform_destroy_command` output if
protocol gateways are enabled (not used here).

## Notes

- **Credentials are never committed.** `*.tfvars` and the generated
  `manifests/weka/core/{weka-client,csi-wekafs-api-secret}.yaml` are git-ignored.
- **WEKA requires a minimum of 6 backend nodes** — `cluster_size` cannot go lower.
- The EBS CSI driver is added in `terraform/20-eks/ebs-csi.tf` via EKS Pod
  Identity (the vendored EKS module ships no addons).
- Terraform modules under `terraform/modules/` are vendored from
  [weka/weka-eks](https://github.com/weka/weka-eks) (`weka-dedicated` model).
